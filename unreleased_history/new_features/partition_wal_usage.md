Added `DBOptions::partition_wal_usage`, which chooses the WAL record format independently of `DBOptions::wal_partitions`: `kNone` keeps today's format, and `kPartitionByColumnFamily` writes indexed records, which more than one WAL requires (with `wal_partitions = 1` it partitions nothing). When set to a value other than `kNone`, each WAL record is tagged with an ordering number (wal_index) that is persisted on disk. The default `kNone` keeps the WAL bit-for-bit compatible with the previous format for downgrade safety. Older RocksDB versions only report indexed WAL records, and in the default point-in-time recovery mode open the DB without them. While indexed WALs may be live, the MANIFEST therefore carries a record that older versions reject, so they fail to open the DB, or a backup or checkpoint taken in that state, instead. To roll back, set `partition_wal_usage` to `kNone` and `wal_partitions` to 1 and reopen in the same open (`kNone` with more than one WAL is rejected), flush every column family, commit or roll back every prepared transaction, wait for the indexed WAL files to be deleted, purge the WAL archive (or wait out `WAL_ttl_seconds` / `WAL_size_limit_MB`), reopen once more with `kNone` and close, then require `ldb check_wal_index` to report no indexed WAL and the guard clear, without setting `partition_wal_usage` back to a value other than `kNone` until it does, before downgrading the binary.
