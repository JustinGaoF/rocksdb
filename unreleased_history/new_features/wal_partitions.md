Added production support for `DBOptions::wal_partitions` greater than 1. When set with a `partition_wal_usage` that enables WAL indexing, writes are spread across that many WAL files for concurrent appends, and recovery merges the partitions back into a single `wal_index`-ordered stream. Values above 1 require WAL indexing (`kNone` with more than one partition is rejected), at most 64, and reject `two_write_queues`, `enable_pipelined_write`, `unordered_write`, `track_and_verify_wals`, `recycle_log_file_num` above 0, `allow_concurrent_memtable_write=false`, `paranoid_checks=false`, and `track_and_verify_wals_in_manifest=false`; the option is not dynamically changeable. Enabling this is a rollout step: every reader of these WALs (ldb, backup and checkpoint restore, RepairDB, secondaries) must run a binary that understands indexed WALs first.
