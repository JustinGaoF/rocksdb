`DBOptions::wal_partitions` values above 1 are now accepted (EXPERIMENTAL). Writes are spread across that many WAL files so that appends to them proceed concurrently; recovery merges them back into one ordered log. It requires `partition_wal_usage` other than `kNone` (the combination with `kNone` is rejected), is limited to 64, cannot be changed with `SetOptions()`, and is rejected together with the options listed in its documentation (for example `two_write_queues`, `enable_pipelined_write`, `unordered_write`, and `track_and_verify_wals_in_manifest = false`). Enabling it is a rollout step: first deploy a binary that understands partitioned, indexed WALs everywhere these WAL files may be read (the DB itself, ldb, backup and checkpoint restore, RepairDB, secondary instances), and only then open a DB with `wal_partitions > 1`. `manual_wal_flush` is supported but not recommended with more than one partition.
